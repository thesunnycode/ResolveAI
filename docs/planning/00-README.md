`task-breakdown` is designed to be run **once per phase**. **All of them are now broken down** — docs 08–16 cover every phase: **241 tasks, 100% of the project planned at task level.** **Start at [14 Task 1](14-TASK-BREAKDOWN-PHASE-1.md), then [16](16-TASK-BREAKDOWN-PHASE-2.md).**

**Note on timelines:** breaking Phases 4 and 5 into tasks revealed that [07](07-DEV-PHASES.md)'s estimates were each about half the real figure — the phase-level numbers counted features, not the tests, DTOs, error paths and plumbing between them. The totals in 07 are corrected to **71–85 working days ≈ 15–18 calendar weeks at 3–4 h/day**. Treat every un-broken-down phase estimate as a lower bound.

**This is a four-to-five month project at the depth it is designed, and no trim makes it ten weeks.** Four phases have each come in at 2–3× their original estimate; cutting Phase 7 entirely saves only 14 days out of 110.

**Scope decision: full — nothing skipped. ~135 working days ≈ 27–28 weeks** at 3–4 focused hours a day. The `⚠️ lean path` markers inside the phase docs are a **pre-agreed contingency cut order**, not recommendations — kept so that if you fall behind, what to drop is already decided.

**The answer to a 27-week project is not a smaller project — it is shipping incrementally.** [12 §The reckoning](12-TASK-BREAKDOWN-PHASE-8.md) has the milestone-resume mapping: by **week 9** (SLA engine + concurrency tests) you already have two resume bullets and something that beats the e-commerce project it replaces; by **week 11**, three; by **week 15**, four; by **week 19**, all five. **Deploy a minimal version right after Phase 6A** so there is always a live URL, and update the resume as each phase lands.

## The one-sentence version

> A helpdesk backend where the AI **never decides anything** — the model emits structured signals, and versioned deterministic policy functions compute every priority, route, escalation and SLA breach.

## The three things that make it not a chatbot

1. **The SLA engine** — business-hours arithmetic, pausable append-only clocks, absolute deadlines polled with `SELECT … FOR UPDATE SKIP LOCKED`, and an escalation ladder that fires exactly once under an at-least-once poller.
2. **Incident correlation** — forty tickets about one outage collapse into one incident behind a deterministic arrival-rate gate. The only place embeddings do something no rule could.
3. **Citation-enforced drafting** — drafts are decomposed into individually-cited claims; any claim whose numbers aren't in its cited span is dropped, and below 0.8 coverage the draft is suppressed entirely.

## Build order, short version

Weeks 1–2 are deterministic backend with **no AI at all**. That is deliberate: the SLA engine is the hardest part and the most likely to slip, so it goes first. If everything after it goes wrong, you still have a real project.

```
W1  Skeleton + ticket lifecycle        (no AI)
W2  SLA engine                         (no AI)   ← hardest
W3  Async pipeline + triage signals
W4  Knowledge base + hybrid retrieval
W5  Citation-enforced drafting
W6  Incident correlation                         ← differentiator
W7  Productionization
W8  README, benchmarks, write-up
```

**Minimum viable resume version:** Weeks 1–3 + 6. Retrieval and drafting (W4–W5) are the most cuttable — counter-intuitive, but correct, since they are also the most common thing in everyone else's portfolio.
